# Тестовый план СМП

---

## 1. Область тестирования и подход

План охватывает всю систему; глубина проверки зависит от риска сервиса.

| Глубина | Сервисы | Как тестируются |
|---|---|---|
| Полная | Authorization, Card-Management | классы эквивалентности, границы, pairwise; unit, API, интеграционные, E2E |
| Средняя | Gateway, Switch, Transaction Logger | классы верхнего уровня, API-тесты, чек-листы |
| Низкая | Bin Lookup, Notification Service, симуляторы, Web Dashboard | дымовая проверка и критический путь |

Подход: тесты проектируются по ТЗ и контрактам API техниками классов эквивалентности, граничных значений и pairwise (PICT); автоматизируются по пирамиде (unit → API → интеграция → E2E → нагрузочный smoke) и запускаются в CI. Окружение: Docker Compose, синтетические данные; каждый тест на лимиты и баланс использует новую карту.

## 2. Критерии входа и выхода

**Вход:** окружение поднято, скрипт дымовой проверки `scripts/smoke-test.sh` проходит; доступны ТЗ и контракты API.

**Выход:**

- выполнены все тесты высокого приоритета и не менее 90 % остальных;
- нет открытых дефектов критического и высокого уровней;
- каждое требование покрыто хотя бы одним тестом;
- покрытие кода Authorization и Card-Management достигло целевого значения;
- зелёный прогон CI приложен к сдаче.

## 3. Критерии приостановки и возобновления

**Приостановка:** окружение не поднимается; Authorization или Card-Management не запускается; нарушена целостность тестовой БД.

**Возобновление:** причина устранена, окружение пересоздано, дымовая проверка проходит.

## 4. Ресурсы

- Люди: тестировщик (студент), куратор (приёмка и уточнение требований).
- Окружение: локальный Docker Compose; GitHub Actions.
- Инструменты: JUnit 5, Mockito, PICT, Docker, `curl` или Postman, RabbitMQ Management UI.

## 6. Риски

| Риск | Снижение |
|---|---|
| Гонки при параллельных транзакциях | отдельные тесты параллельности, нагрузочный smoke |
| ТЗ и реализация расходятся | список наблюдений в `test-design.md`, уточнение у куратора |
| Нестабильные тесты из-за асинхронной записи в журнал | ожидание с таймаутом вместо фиксированных пауз |
| Зависимость тестов от накопленного состояния | новая карта на каждый тест |
| Не хватает времени | выполнение по приоритетам |

## 7. Метрики

- покрытие требований тестами — 100 %;
- доля пройденных тестов: высокий приоритет — 100 %, остальные — не ниже 90 %;
- открытые дефекты критического и высокого уровней — 0;
- покрытие кода ядра — не ниже целевого - пусть 70 %;
- для нагрузки: p95 - пусть 350 мс, p99 - пусть 500 мс, доля ошибок - пусть 5 %.
